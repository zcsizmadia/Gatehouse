# Security policy

Gatehouse sits in the request path between applications and model providers, and
it holds provider credentials. We treat it as security-critical infrastructure.

## Reporting a vulnerability

**Please do not open a public issue.**

Use GitHub's private vulnerability reporting:
[**Report a vulnerability**](https://github.com/zcsizmadia/Gatehouse/security/advisories/new).
It is enabled on this repository and delivers straight to the security response
team listed in [MAINTAINERS.md](./MAINTAINERS.md).

What to expect:

| Stage                   | Target                                     |
| ----------------------- | ------------------------------------------ |
| Acknowledgement         | 3 business days                            |
| Initial assessment      | 10 business days                           |
| Fix or mitigation plan  | 30 days for high/critical                  |
| Public advisory         | On release, or 90 days, whichever is first |

We will credit you in the advisory unless you ask us not to. There is no bug
bounty; we would rather be honest about that than imply one.

## Supported versions

Pre-1.0, only the latest release receives fixes. After v1.0, the support policy
becomes part of the API stability guarantee and will be stated here explicitly.

| Version | Supported           |
| ------- | ------------------- |
| 0.x     | Latest release only |

## Supply chain

Verification material ships with every release rather than being promised for
later. Each release includes:

- **Signed artifacts** — keyless [Sigstore](https://www.sigstore.dev/) signatures
  via cosign, with the certificate identity bound to this repository's release
  workflow.
- **SBOM** — CycloneDX, one per published artifact.
- **SLSA Build Level 3 provenance** — generated by the reusable GitHub-hosted
  builder, attesting which workflow at which commit produced the binary.

### Verifying a release

Verify the Sigstore signature and its provenance identity:

    cosign verify-blob gatehouse-linux-x64 \
      --bundle gatehouse-linux-x64.sigstore.json \
      --certificate-identity-regexp "^https://github.com/zcsizmadia/Gatehouse/.github/workflows/release.yml@refs/tags/v.*$" \
      --certificate-oidc-issuer https://token.actions.githubusercontent.com

Verify the SLSA provenance:

    slsa-verifier verify-artifact gatehouse-linux-x64 \
      --provenance-path gatehouse-linux-x64.intoto.jsonl \
      --source-uri github.com/zcsizmadia/Gatehouse

If verification fails, treat the artifact as compromised and tell us.

## Threat model

Gatehouse's own security posture, stated plainly so you can check our work.

**What Gatehouse defends against**

- Provider API keys leaking to client applications — clients hold virtual keys
  and never see upstream credentials.
- A compromised client exhausting an organisation's spend — budgets are enforced
  server-side, before the upstream call.
- Untracked model usage — every request is recorded in an audit log that the
  requesting application cannot write to.

**What Gatehouse does not defend against**

- A compromised Gatehouse host. It holds provider credentials; treat the host as
  a secrets-bearing tier and isolate it accordingly.
- Prompt injection reaching the model. Gatehouse can redact and can block on
  policy, but it is not a semantic firewall and will not claim to be.
- Malicious models. Gatehouse governs access, not model behaviour.
- Denial of service against upstream providers by an authorised, in-budget
  caller. Rate limits mitigate; they do not eliminate.

## Hardening guidance

- Run as an unprivileged user. The systemd unit and the container image both do
  by default.
- Terminate TLS in front of the gateway, or configure Kestrel's certificate.
  Never run the admin surface in plaintext.
- Store provider credentials in a secret store, not in `appsettings.json`. Azure
  managed identity requires no stored credential at all and is the recommended
  path for Azure OpenAI.
- The admin API and the inference API can be bound to separate ports. Do so, and
  expose only the inference port to application networks.
